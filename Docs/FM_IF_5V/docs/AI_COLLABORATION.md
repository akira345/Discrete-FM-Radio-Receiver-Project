# アナログ回路の自作に生成AIを使う ── 実践ナレッジ

**対象**：ディスクリートの高周波アナログ回路を、生成AIを設計パートナーとして自作する人
**元プロジェクト**：5V FM IF ストリップ（4段差動リミッタ ＋ ギルバート型クワドラチャ検波）
**使用環境**：Claude Opus 5 / 思考レベル「高」 / Cowork（ngspice・Python が動くサンドボックス付き）
**結果**：キャプチャ閾値 0.37 mVrms、検波直線性 1.0 %、完成まで約3日

この資料は成功談ではなく、**AI が具体的にどこで間違えたか、それをどう検出したか**の記録です。
そこが第三者にとって最も価値のある部分だと考えます。

---

## 0. 最初に：この方法が成立した条件

1. **AI が自分で検算できる実行環境があった**
   ngspice をその場で走らせられたことが決定的でした。AI の主張を AI 自身に否定させられます。
   実行環境がない場合、この資料の多くは成立しません（人間が全部 LTspice に打ち込むことになる）。
2. **人間の側に測定器があった**
   オシロと Analog Discovery 3。**AI の誤りの大半は実測で潰れました。**
3. **人間が電子回路の基礎を持っていた**
   AI が「それらしい嘘」を言ったときに違和感を持てるかどうかが分かれ目です。
   完全な初心者が AI だけで高周波回路を組むのは、現時点では厳しいと思います。
4. **思考レベルを高くした**
   定量的な議論（インピーダンス、結合容量、dB バジェット）の精度が明確に変わります。

---

## 1. AI が実際に間違えたこと（IF 部 13件 ＋ MPX デコーダ編 17件）

**これが本題です。** どれも自信たっぷりに、もっともらしい説明付きで出てきました。

### 1.1 物理法則の適用ミス

| # | AI の主張 | 実際 | 検出方法 |
|---|---|---|---|
| 1 | 「4段目出力 3.61 Vpp は物理的にありえない。静止電流 × コレクタ抵抗を超えている」 | **抵抗テールでは過大入力時にエミッタノードが入力に追従し、瞬時電流が静止電流を超える。** シミュレーションでも 3.33 Vpp | **ngspice で再現させた** |
| 2 | 「Cπ は約 30 pF、ベースインピーダンスは 494 Ω、結合損失 2.2 dB」 | 実際は Cπ ≒ 85 pF ＋ ミラー効果 220 pF で **約 50 Ω**。桁が違う | ngspice で入力インピーダンスを実測（`.ac` ＋ 電流注入） |
| 3 | 「次段がコレクタを約 50 Ω に負荷する（ミラー効果）」 | ngspice では **1.8 kΩ**。コレクタノードは 330 → 278 Ω にしか下がらない | 同上 |

**教訓**：AI の「〜のはず」は**必ず数値で言わせ、その数値をシミュレータに投げる**。

### 1.2 測定の原理的な限界を見落とす

| # | AI の主張 | 実際 |
|---|---|---|
| 4 | 「共通エミッタ電圧が 0.6〜0.9 V なら片側だけ導通している」 | **Vbe は電流が2倍になっても 18 mV しか動かない。** エミッタ電圧では何段導通しているか判別できない。正しい指標はコレクタ電圧か電源電流 |
| 5 | 「200 mV/div で見てノイズも発振も見えないので、バイアス経路は白」 | **利得 76 dB に対して発振に必要な帰還は 0.2 mV。** そのレンジでは原理的に見えない |
| 6 | 「測定の床が 305 mVrms あるのではないか」 | プローブ先端をグラウンドクリップに短絡したらほぼゼロ。仮説は即座に否定された |

**#5 は最も高くついた誤りです。** この誤判断によって「伝導結合」という真因の仮説を一度消してしまい、
遠回りしました。**AI の誤りを見つけたら、その誤りが過去のどの判断を無効化したかまで遡らせること。**

### 1.3 実験計画の失敗

| # | 内容 |
|---|---|
| 7 | 「ダンピング抵抗を 1kΩ → 220Ω に変えて 2.5 dB の変化を見る」という実験を設計した。**対象はパルス性ノイズで、単発測定のばらつきが 2.5 dB をはるかに超える。** 何も分からない実験だった |

**教訓**：AI に実験を設計させたら、**「その差は測定のばらつきより大きいのか」を必ず聞く。**

### 1.4 判定基準が現実離れ

| # | AI の主張 | 実際 |
|---|---|---|
| 8 | 「OA と OB は 50 mV 以内に揃うはず」 | 実測 146 mV。これは ΔVbe わずか 2.3 mV に相当。ディスクリートの Vbe ばらつき ±5 mV を考えれば **±300 mV が妥当**。IC の中の話をディスクリートに持ち込んでいた |

### 1.5 モデルの捏造

| # | 内容 |
|---|---|
| 9 | **2SK3557 の SPICE モデルを勝手に作った**（VTO=-1.2 / BETA=8m）。根拠は何もない「それらしい値」。これを元に「BL1 の駆動が 20 % 低くなる」と警告したが、**方向すら逆**だった。実測 SF = 0.662 V から逆算すると Vp ≒ -0.771、IDSS ≒ 15 mA（データシートの 10〜20 mA に整合）で、実際は設計より **良い** 側 |

**教訓**：**デバイスモデルは出典を必ず聞く。** 「メーカー提供」「データシートからフィット」「推定値」は
天と地ほど違います。推定値なら、実測から逆算し直すこと。

### 1.6 空間認識（最も弱い領域）

| # | 内容 |
|---|---|
| 10 | **SOT-23 のパッケージ端子配置を鏡像に描いた。同じ誤りを2回。** SOT-23 は B と E が片側、C が反対側に1本で、**裏返して配置することはできない**。AI はこれを「対称な三角形」として扱ってしまう |
| 10b | **JFET のドレインとソースを取り違えた。別プロジェクト・別 AI でも同じ誤り。** フロントエンドでは実機の J2 が逆接続で実装されており、IF 部でも「VCC につながる方がソースでしたっけ」という混乱が起きました。**回路記号が D と S を区別しない**ことが根本原因です |
| 11 | コレクタにぶら下がる 1000p を **GND ではなく VCC** に落とした。交流的には等価だが、テール抵抗と同じ GND バスに戻さなければリターン電流の経路が変わる |

**#10 への対策として有効だったのは、機械的な検算式を作らせることでした。**

```
すべてのトランジスタについて  sign( (B→E) × (B→C) )  を計算し、
全個体で符号が一致することを確認する
```

AI に「目で見て確認しろ」と言っても直りませんが、**外積の符号という計算に落とすと検出できます。**
**実装図・基板図は必ず人間が最終確認してください。** ここは現時点の AI の明確な弱点です。

### 1.8 最大の失敗：DC 動作点を確認せずに AC 解析を信じた

**同一セッション内で同じ誤りを2回繰り返し、しかも1回目の「訂正」も誤りでした。**

| 回 | やったこと | 結果 |
|---|---|---|
| 1 | ギルバートセルの出力（**電流源**）を「電圧源＋1.5 kΩ」で駆動 | 源インピーダンスを二重計上。53 kHz で −2.3 dB と報告（誤り） |
| 2 | トポロジは直したが、**電流源の符号を逆**にした | DC 動作点が壊れた（ノードが電源電圧を超えた）状態で AC 解析。「フラット（−0.19 dB）」と報告（誤り） |
| 3 | DC 動作点を実測値と照合してから AC | **正解：−3.93 dB**。セパレーション上限 13 dB という設計欠陥が判明 |

1回目の誤りをユーザーに指摘される前に自分で気づいて訂正したのですが、
**その訂正自体が別の誤りを含んでいた**ため、かえって「問題なし」という誤った安心を与えてしまいました。

**教訓**：

```
AC 解析・過渡解析の結果を採用する前に、必ず .op を実行して
主要ノードの DC 電圧を実測値（または手計算）と照合する。
```

線形化解析は DC 動作点まわりで行われるので、**動作点が壊れていれば AC の結果は全部でたらめ**です。
しかもエラーにはならず、もっともらしい数値が出てきます。
本プロジェクトでは実機の実測値（OB 3.276 V）という照合先があったため検出できました。

### 1.9 MPX デコーダ編で間違えたこと（2026-09 追記・17件）

IF 部の完成後、MPX デコーダのデバッグで再び AI の誤りが続きました。
**IF 部とは性質が違い、大半が「測定の指示」の誤りです。** 人間が毎回測り直すことになりました。

| 分類 | AI の誤り | 実際・検出方法 |
|---|---|---|
| 測定設定 | FFT を Stop 2 kHz にするよう指示 | サンプリング 4 kHz で 19/37/39 kHz が 1 kHz に**折り返す**。人間の「FFT の端で測るのは無理では」の指摘で撤回 |
| 測定設定 | 表示レンジ（5.2 Vpk2pk）を信号レベルと読んだ | パイロット漏れを 66 dB と過大評価。実際は約 36 dB |
| 測定設定 | 入力範囲を確かめずに 1 Vpp（設計値の10倍）を指示 | 過入力でパイロット位相が動く領域だった |
| 測定設定 | ファイルごとの正規化を忘れ、パイロット単体を 10 倍で出させた | 20.7 mV で再測定 |
| 測定設定 | Flat Top 窓で 1977.5 Hz と 2002 Hz を区別できる前提で議論 | 窓の分解能で原理的に分離できない |
| 実験計画 | P1〜4 × T1〜4 の全組み合わせ（16 通り）を要求 | 人間に指摘されて絞り込み。**ダイナミックレンジの確認も抜けていた** |
| 実験計画 | RV2 を回させる前に「現在位置に印を」と言わなかった | 位置が失われ最初からやり直し |
| モデル | 回路図を見る前にマトリクスを仮定し「L と R は逆に動くはず」 | 実回路は両方同時に動くのが正しい。**ネットリストを読んでから撤回** |
| モデル | 「経路利得が 14 dB 高い＝注入点が違う」 | 誤り。撤回 |
| モデル | ステレオ判定の SPICE で「パイロット無しでもステレオ判定」 | 実機と矛盾。撤回 |
| 部品名 | 教科書の MFB の記号「R3」で呼んだ | 実基板の R3 は別の抵抗（Q2 のエミッタ）。**実回路の部品番号で話すこと** |
| 仮説 | R37 を 2.2 k にして立ち上がりを速く | 遅く見えたのは ×1 プローブの容量。不要 |
| 仮説 | SOT-23（Q3〜Q6）の逆実装を疑う | ゲート駆動の実測で否定 |
| モデル | 次期案のシミュレーションで、オペアンプモデルの内部を ±5 V で制限したため**スルーレートが実質 0.003 V/µs** になり、位相比較器に 25° の偽の誤差が出た | ループを切って位相比較器だけを動かし、**理論式（−(2/π)·P·sinψ）と照合して発見**。SR を明示したモデルに修正 |
| 解析 | 検波後 LPF で「受信機全体のセパレーション上限 35.2 dB」と結論し、複数の資料に書いた | L−R 全体が 53 kHz の減衰を受ける最悪値で、**マトリクス（RV2）による補正を無視していた**。両側波帯と 1 kHz での補正を入れると約 58 dB。V4 の検討で入力レベルを見直す際に再計算して発覚。**「上限」を主張するときは、その後段で補正されないかを確認する** |
| 部品 | NJM2747 を「レール・ツー・レール入出力（RRIO）」と説明した | データシートでは**出力のみ**レール・ツー・レール、入力同相範囲は 0〜4 V。**ユーザーがデータシートを添付して確認**。結論（2 Vpp で問題なし）は変わらなかったが、入力が 4 V に近い箇所（U2A の＋入力）の注意点が新たに出た。**部品の仕様は記憶で語らせず、データシートで確認させる** |
| 予測 | 1.5 k 並列後に「約 30 dB」と予測 | 実測 14 dB（RV2 の再調整が必要だった）。**モデルが RV2 の絶対位置を決められなかった** |

**教訓**：

```
測定を指示する前に、AI 自身に次の4点を確認させる。
  1. エイリアシング（サンプリング周波数と信号帯域）
  2. ダイナミックレンジ（見たい漏れが測定の床より上か）
  3. 被測定回路の入力範囲（設計値の何倍を入れるのか）
  4. 調整箇所の現在位置の記録
```

**回路図（ネットリスト）を渡す前の AI の推論は、どれだけもっともらしくても仮説にすぎません。**
本件では、ネットリストを渡した時点で AI の回路モデルが2回書き換わりました。**不具合の相談は回路図を最初に渡すこと。**

### 1.7 その他の反復的な不具合

- `numpy.ndarray.ptp()` の削除に気づかない（`np.ptp()` を使う）
- ngspice の `meas` に `db(v(x))` をインラインで書けないことを繰り返し忘れる
- ヒアドキュメント経由で `\uXXXX` エスケープが解釈されてしまう文字列置換の失敗
- **matplotlib のラベル衝突**。図を作らせると必ずテキストが重なる。何度も直させる必要がある
- **単位計算のミス**。mV/kHz の傾きが延々と 0.01 と表示され続け、結局手計算した

## 2. 効いた進め方

### 2.1 前提を毎回、明文化して渡す

このプロジェクトでは以下を「動かせない前提」として固定し、議論のたびに参照させました。

```
・学習目的（ICの中身が知りたい）。性能で市販品に勝つ必要はない
・電源 5 V 単一
・IF 10.7 MHz、日本ワイドFM 76〜95 MHz
・SMD 1608 / SOT-23 を 2.54mm 万能基板に実装（裏面は GND メッシュ）
・感度はIF段で決まる。RFアンプではない
・後段は 74HC4046 の MPX デコーダ
  → 検波出力は 19kHz パイロットと 38kHz 副搬送波を通す必要がある
  → デエンファシスも 15kHz LPF もここには入れない
・検証は ngspice
```

**特に最後の項目（MPX が後段にある）は、放っておくと AI が「FM 検波だから
デエンファシスを入れましょう」と善意で提案してきます。** 前提を書いておくと防げます。

### 2.2 「たぶん大丈夫」を許さない

すべての判断を pF、dB、mV、Ω に落とさせる。これが最も効きました。

**実例：迷結合バジェット**

「4段目が発振している」に対して、AI に発振条件を定量化させた結果：

| ループ | 発振に必要な結合容量 |
|---|---|
| 4段ループ | **0.035 pF** |
| 3段ループ | 0.208 pF |
| 2段ループ | 2.06 pF |
| 4段目単独 | 20.7 pF |

この表があると、「4段目だけの問題ではない（単独発振には 20 pF 必要）」と即断でき、
切り分けの順序が決まります。**「なんとなく配線を離す」から「0.035 pF を切る」に変わります。**

### 2.3 予測 → 実測 → 差分の説明、を毎回回す

**測定する前に AI に期待値の表を出させる**のが重要です。後出しだと何とでも言えます。

実例（S カーブ測定の前に出させた予測）：

| 周波数 | 予測 | 実測 |
|---|---|---|
| 10.625 | 2.41 V | 2.368 |
| 10.700 | 2.78 V | 2.760 |
| 10.775 | 3.12 V | 3.164 |
| 感度 | 5.0 mV/kHz | 5.375 |

一致すれば設計理解が正しい。ずれれば、**そのずれ自体が次の情報**になります。

### 2.4 比を見る（絶対値より強い）

測定系の校正が怪しいとき、**絶対値は信用できないが比は信用できます。**

```
SF 実測 317 mVpp （予測 366） ← 87 %、校正誤差かもしれない
BL1 実測 213 mVpp （予測 239） ← 89 %、同上
比   実測 0.672   （予測 0.653）← 3 % 以内で一致 ← ここが決定的
```

比が合っている＝回路は設計通り。実際、後で駆動振幅の校正がずれていたことが判明しましたが、
比を見ていたおかげで回路の健全性は先に確定していました。

### 2.5 切り分けは二分探索として設計させる

「発振している」→「段を1つずつ外して、どこから始まるか」。
AI に**手順を先に書かせてから**実行すると、途中で目的を見失いません。

### 2.6 DC だけで判定できる指標を作らせる

高周波の測定は難しく、プローブを当てること自体が回路を変えます。
**DC 電圧だけで異常を検出できる指標があると圧倒的に楽です。**

本プロジェクトでの最大の発見はこれでした：

```
BA = VB − Ib × RGA
　　正常  : 1.99 V （Ib = 13.5 µA）
　　発振中: 1.5〜1.6 V （Ib = 57 µA）← ベース整流＝Class-C動作＝発振の指紋
```

テスタ1本、8点測るだけで4段すべての発振有無が分かります。
さらに **Vbe が 0.25 V という値は導通中の BJT では物理的にありえない**ので、
測定値の異常さ自体が診断になりました。

**AI に「この故障モードを DC 電圧で検出する方法はないか」と聞くのは、非常に費用対効果が高い質問です。**

---

### 2.7 仮説を検証するための試験信号を作らせる

MPX デコーダでは「パイロット経路が 37° 遅れている」という仮説を、**回路を一切触らずに**確かめました。
パイロットの位相だけを ±37° ずらしたコンポジットを AI に生成させ、AD3 で入力しただけです。

| 試験信号 | 結果 |
|---|---|
| +37°（遅れを先に打ち消す） | セパレーション 31.5 dB に改善 |
| −37°（さらに遅らせる） | L と R が入れ替わる |

**両方向で予測どおりに動いたので、原因と向きが同時に確定しました。**
回路を改造して確かめる方法だと、改造自体が別の変化を持ち込みます。
「**この仮説が正しいときだけこう動く信号**」を作れないか、AI に聞く価値があります。

### 2.8 振幅だけでなく位相を読む

FFT の位相の列を見ると、漏れが主信号と**同相か逆相か**が分かります。
「RV2 が小さすぎるのか大きすぎるのか」が1回の測定で決まり、闇雲に回す必要がなくなりました。

### 2.9 専用 IC と比べさせる

行き詰まったとき、「かつての専用 IC はどうしていたか」を AI に聞くと、構造的な問題が見えました。
本件では、IC がパイロットを BPF で取り出さずコンポジットを直接同期検波していることから、
**自作回路の弱点が「位相精度が要る経路に高 Q フィルタを置いたこと」**だと分かりました。
IC を作り直すという学習目的にも直結する質問です。

## 3. AI が特に弱い領域（今回の観測）

| 領域 | 症状 | 対策 |
|---|---|---|
| **パッケージの端子配置・基板レイアウト** | SOT-23 を鏡像配置。同じ誤りを繰り返す | 機械的な検算式に落とす。**最終確認は必ず人間** |
| **3端子デバイスの向き（特に JFET）** | D と S を取り違える。回路記号で区別できないため AI も人間も間違える。**2つの独立したプロジェクトで発生** | データシートのピン番号を必ず明記させる。テスタでは D/S を判別できないことを前提に手順を組む |
| **デバイスモデル** | 実在しないモデルを自然に捏造 | 出典を必ず聞く。実測から逆算させる |
| **測定のばらつき** | 分散に埋もれる実験を設計する | 「その差はばらつきより大きいか」を毎回聞く |
| **図版のレイアウト** | テキストが重なる | 生成した図は必ず目視。何度か直させる前提で |
| **単位換算** | mV/kHz などで桁を間違える | 重要な数値は手計算で検算 |
| **DC 動作点の未確認** | 動作点が壊れた状態の AC/過渡解析を信じる。**エラーにならないので気づけない** | 解析前に必ず `.op` を実行し、実測値と照合する |
| **自分の誤りの波及** | 訂正しても、その誤りが無効化した過去の判断に戻らない | 「その誤りは過去のどの結論を変えるか」と明示的に聞く |
| **測定条件の事前確認** | エイリアシング・レンジ・入力範囲を確認せずに測定を指示する。**MPX 編の誤りの大半** | 1.9 節の4点を AI に確認させてから測る |
| **回路図を見る前の推論** | 一般的な回路を仮定して説明を組み立てる | 不具合の相談は回路図・ネットリストを最初に渡す |
| **長期記憶** | 会話が長くなると初期の情報が失われる | 次章 |

## 4. セッション管理（実際に失敗した点）

**本プロジェクトでは、フロントエンド部の設計議論が丸ごと失われました。**

長い対話はコンテキスト圧縮を受け、古い部分は要約に置き換わります。
要約には「2SK3557 を使ったフロントエンドは製作済み」としか残っておらず、
回路構成も定数も調整方法も復元できませんでした。

**対策：**

1. **節目ごとにドキュメント化させ、ファイルとして保存する。** 会話の中に情報を置かない
2. **ネットリスト・スクリプトはファイルで持つ。** 会話に貼るだけだと消える
3. **実測値は表にしてファイルに書き込む。** これが後の全ての判断の土台になる
4. ブロックが1つ完成したら、**次に進む前に**そのブロックの資料を作る

本プロジェクトの IF 部は `HANDBOOK.md` に残せましたが、フロントエンドは失いました。
**この差は、途中でファイルを作ったかどうかだけです。**

## 5. プロンプトの実例

### 良い報告（実際に効いたもの）

```
原因がわかりました。４段目で発振しています。
３３０オームで入力を終端して測定しました。
３段目までは雑音のような波形ですが、４段目を通すと左側で１６MHz、右側で２MHzでした。
また４段目だけは各部の電圧が他と違いました。
VBiasの10kとベース抵抗47オームとの交点
　１～３段目：１．９５V ／ ４段目：１．５～１．６V
共通エミッタ（150オーム）
　１～３段目：１．２８V ／ ４段目：１．３V
格段の電源は22オームと10uFで独立して供給しています。
```

**なぜ良いか**：測定条件（終端の有無）、測定場所（部品名で特定）、数値、比較対象（他段）、
回路の状態（電源分離）が全部入っている。ここから「ベース整流」という診断に一直線でした。

### 悪い報告

```
発振しているようです。どうすればいいですか
```

AI は一般論のチェックリスト（デカップリングを入れろ、配線を短くしろ）しか返せません。

### 報告のテンプレート

```
【症状】
【測定条件】プローブ倍率／結合／レンジ／時間軸／終端の有無
【測定場所】部品名またはノード名で特定
【数値】正常な箇所との比較を含める
【回路の状態】どこまで実装済みか、何を外しているか
【変更履歴】前回から何を変えたか
```

### 議論を始めるときの初期プロンプト（テンプレート）

```
以下の回路を自作します。設計パートナーとして議論してください。

【目的】（学習／実用／性能目標）
【動かせない前提】電源電圧／周波数／使用デバイス／実装方法／後段の回路
【現在の状態】どこまでできているか

【検証手段】ngspice / LTspice / 実測

お願い：
・判断は必ず数値（pF, dB, mV, Ω）で示してください
・シミュレーションで確認できることは実際に走らせて確認してください
・デバイスモデルを使う場合、出典（メーカー提供／実測フィット／推定）を明記してください
・私が測定する前に、期待値の表を先に出してください
```

## 6. チェックリスト：AI の提案を受け取ったとき

- [ ] その主張は**数値**になっているか。「たぶん」「だいたい」で終わっていないか
- [ ] その数値は**シミュレーションか実測で裏が取れる**か。取ったか
- [ ] **デバイスモデルの出典**は明示されているか。推定値ではないか
- [ ] 判定基準は**ディスクリート部品のばらつき**を考慮しているか（IC の中の話をしていないか）
- [ ] 提案された実験は、**測定のばらつきより大きい差**を見るものか
- [ ] **基板図・端子配置は自分の目で確認したか**（ここは AI を信用しない）
- [ ] 「見えないから白」という論法を使っていないか。**測定レンジで見える量なのか**
- [ ] 前回の誤りが訂正されたとき、**それが無効化した過去の結論**に戻ったか
- [ ] 測定の指示は、**エイリアシング・ダイナミックレンジ・入力範囲**を確認済みか
- [ ] 調整箇所を触る前に、**現在位置を記録**したか
- [ ] AI は**実回路の部品番号**で話しているか（教科書の記号になっていないか）

## 7. 総括

生成AIは、この規模のアナログ回路設計において**強力だが、検算なしには危険**です。

**強かったところ**
- トポロジーの選択と定数の初期設計（ギルバートセル、TA7061 方式のバイアス、タンクのダンピング）
- 故障モードの物理的な説明（ベース整流、スケッギング、キャプチャ効果）
- 「DC 電圧だけで発振を検出する」のような、診断手法そのものの発明
- 帯域外利得ピークの発見（10.7 MHz ではなく 2.61 MHz でループが閉じる）
- 大量の定量計算を厭わないこと

**弱かったところ**
- 空間認識（端子配置・レイアウト）── **3端子デバイスの向きは2プロジェクトで繰り返し間違えました**
- 存在しない情報の捏造（デバイスモデル）
- 自分の誤りの波及範囲を追えないこと
- 測定のばらつきの感覚

**結論として、役割分担はこうなります。**

| | 担当 |
|---|---|
| トポロジー選択・定数設計・物理的説明 | AI |
| シミュレーションによる検算 | AI（ただし人間が「走らせたか」を確認） |
| 実測 | 人間 |
| 基板レイアウトの最終確認 | **人間** |
| 矛盾の指摘 | **人間**（ここが一番重要） |

**AI の誤りを実測で潰す作業こそが、このプロセスの本体です。**
AI が正しかったから完成したのではなく、**AI が間違えたことを測定で発見し続けたから**完成しました。

逆に言えば、測定器を持たずに AI とだけ対話していたら、
「4段目出力 3.61 Vpp は物理的にありえない」「バイアス経路は白」といった誤った結論を抱えたまま、
おそらく完成しなかったと思います。
